# Project standards

Mandatory for every pipeline project sprint in this repository (user rule, 2026-11-12). These rules outrank the tier exemptions in [workflow policy](../../.claude/skills/apiv-method/references/workflow-policy.md) for project code: a Low documentation fix stays exempt, any change to project code, SQL, tests, Docker or data does not. "First working version" means the smallest real version, never a dummy: real engines, real files, measured numbers.

## 1. Everything that runs lives in the repo

- Every SQL statement, Python module, shell script, Dockerfile, compose file, config and seed dataset that a run uses is a committed file in the project folder. No SQL or Python typed into `docker exec`, a REPL or a notebook cell as the only copy.
- SQL lives in `sql/<stage>/*.sql`, not as inline strings. Python lives in `src/<package>/` (library) and `scripts/` (entry points). Containers mount the repo; nothing is edited inside a container.
- Every run is reproducible from one `make` target that maps 1:1 to a `scripts/` entry point. A step that cannot be reproduced from the repo did not happen.
- Layout: `pyproject.toml`, `Makefile` (Docker files only when a container is used), `data/`, `sql/`, `src/`, `scripts/`, `tests/`, `results/`, `README.md`.

## 2. Tests first, tracked in the repo

- Tests live in `<project>/tests/` and are listed in `tests/CATALOG.md`: test name, behavior, the break it catches, layer (unit or integration), sprint, status (RED seen, GREEN).
- Write the test before the code. Run it, capture the failing output to `results/<sprint>/run/red.out`, then implement until it passes and capture `green.out`. A test never seen failing is unproven.
- Every new suite gets a mutation check (break the code on purpose, a test must fail); record the mutation and result in the catalog.
- Standards check before any result is reported: `ruff check`, `ruff format --check`, `pyright`, `sqlfluff lint sql/`, `pytest`. Output saved under `results/<sprint>/run/`.

## 3. Ponytail review of code and tests

- After a sprint's code and tests are written, run `ponytail-review` once on the code and once on the tests. The test review asks: does each test fail for a real defect, are expectations hand-derived (no mirror assertions), is any test missing for a stated behavior.
- Fix the findings, rerun the standards check, record findings and fixes in `results/<sprint>/review.md`. One pass per sprint; re-review only when a fix changes behavior.
- Find problems before the user does. A defect the user has to point out goes to `ledger/lessons.md`.

## 4. Results page for all sprints

- Each project keeps one `results/index.html` covering every sprint, newest first. It is generated by a committed script (`scripts/build_results.py`) from captured files, never hand-typed, so it always matches the runs.
- Per sprint it shows: goal and pattern; as-built architecture (stack-diagram PNG); scripts and SQL used (repo paths); exact commands; terminal output verbatim from `results/<sprint>/run/*.out`; tables before and after with schema, row counts and sample rows; data metrics the pattern changes (file counts, file sizes, snapshots, segments, timings); test results RED and GREEN; review findings; known limits.
- The reader learns what a run did from the page alone, without running anything.
- Render the page to PNG (Playwright, as stack-diagram does) and look at it before reporting.

## 5. Captures with stack-diagram

- Every sprint produces an as-built architecture diagram with the `stack-diagram` skill: source `.src.html`, built `.html`, PNG light and dark, inspected.
- Tables, terminal output and metrics go into the results page in the same visual style (stack-diagram fonts and palette). stack-diagram draws topology; the results page carries data.
- Every number on the page names its source file, command and run time.
