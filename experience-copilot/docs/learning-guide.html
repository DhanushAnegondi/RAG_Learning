CHAPTER 01

The project, without the buzzwords

Search your evidence. Choose the right answer shape. Extract facts where possible; generate and check prose where useful.

ACTIVE PERSONAL INDEXKeyword search

8 selected source documents, 70 passages at the documented November 2 snapshot.

IMPLEMENTED, INACTIVE HEREHybrid vector search

Chroma + NVIDIA embeddings + keyword search. Personal embedding builds returned service errors.

NO MODEL TRAININGCode + prompts + evidence

No weights were trained. Temperature remains 0; language-model judgments can still vary.

RAG means retrieval-augmented generation: find relevant source material and provide it to a model when it writes an answer. A source-extraction path is also valuable: a technology list can be rendered from a stack document without asking a model to rewrite it.

The website is a local Streamlit interface. It is not the whole system. Behind it are document preparation, search, source selection, writing instructions, citation checks and failure handling. The personal library contains selected excerpts, not every practice file in the original folders.

Read the status labels carefully. “Confirmed” means the source is approved for this application's evidence library. It is not independent proof of employment, production deployment or a metric. A model-approved answer is not a human-certified answer.

Two different times of work

Preparation time

When a document changes: load, label, chunk and rebuild the index. This is not training.

Question time

For each question: choose shape, retrieve evidence, select a route and display a sourced answer or clarification.

CHAPTER 02

Prepare the documents

Ingestion turns files into searchable passages while retaining their origin.

  1. Load supported text. The current loader reads MD/TXT directly and extracts existing PDF text with pypdf.
  2. Read evidence.json. Each source can declare employer, status, ownership, project, version and story ID. Unlisted files default to unverified.
  3. Split at headings. Markdown headings create section boundaries before recursive character splitting.
  4. Retain bounded context. Search small passages; attach the surrounding section when it is no more than 4,000 characters. Larger sections keep individual context identities so selected fragments are not lost.
  5. Publish a snapshot. Stable hashes identify content; hybrid snapshots use content-addressed collections. The active JSON pointer changes after a successful build.

Example manifest — illustrative, not a claim

{
  "documents": {
    "Employer/project.md": {
      "status": "unverified",
      "employer": "Employer",
      "project": "Documented project",
      "ownership": "Precisely what I contributed",
      "version": "reviewed-source-version",
      "story_id": "project-story"
    }
  }
}

Only change a source to confirmed after reviewing it. Other statuses are draft, synthetic and unverified. Split mixed factual/practice files before confirming them; this initial schema labels whole files, not individual claims.

Chunking is a tradeoff. Small chunks improve precise matching but can separate an action from its result. Overlap repeats boundary context. Large chunks preserve context but can add unrelated details. These settings are measured in characters here, not tokens.

Current implementation limits: heading recognition is based on regular expressions, not a full Markdown parser. Old hybrid collections are retained for recovery. Concurrent ingests into the same path are not protected by a production-grade locking protocol.

CHAPTER 03

Follow a question through the app

Choose an example and step through the route. This is a teaching simulation; it makes no model calls and does not change the app.

Question types are rules, not a trained classifier

question.py uses text patterns to recognize stack questions, introductions, behavioral stories and direct questions. It also expands some search queries. Mixed questions about a story and its tools retain the story format. Unusual wording can still be missed; rules need regression examples.

Introductions consider multiple experience labels before the model selects supporting evidence. A vague introduction should not require a title, date or metric at every employer. Conversely, a leadership question needs a documented leadership episode; a technical task list cannot establish direct reports.

CHAPTER 04

Search, rank and choose evidence

Finding a passage and proving it supports an answer are different jobs.

ConceptWhat it means hereImportant boundary
BM25 keyword retrievalMatches query terms with term-frequency, rarity and passage-length scoring. This is active for the personal index.Strong on exact terms; paraphrases without matching words can be missed.
Dense retrievalConverts passages and queries to numerical vectors, then uses similarity search in Chroma.Implemented but inactive for the current personal index; not a written answer and not model training.
RRF fusionCombines ranked lists with the sum of 1/(60 + rank).Used by hybrid search; it combines ranks, not incompatible raw scores.
Source filteringV2 allows confirmed sources and can scope to an employer explicitly selected or literally recognized in the question.Literal matching can miss employer aliases. A source label is not a universal entity resolver.
LLM evidence selectionThe chat model selects passage IDs and judges whether evidence is sufficient.This is model-based ranking, not a dedicated cross-encoder reranker. It can be too cautious or wrong.
Quote-backed recheckSome insufficient decisions get a second model check that must quote selected text.An exact quote establishes provenance, not logical entailment.
Hybrid RRF scorescore(passage) = Σ 1 / (60 + position in each ranked list)

Most retrieval paths initially consider up to 24 candidates and select up to six evidence passages. Stack and introduction paths have special source-priority/diversity rules. More candidates can recover missing evidence but also increase distraction, latency and model-call cost.

The stack fix: a simple technology-name question with a reviewed dedicated Stack_and_Tools.md source selects source sections and extracts their bullet names. It preserves categories and citations instead of generating a narrative and asking another model whether that list is acceptable. Questions asking how technologies were used can still take the generated-answer route.

CHAPTER 05

Write, check and repair the answer

The generated path keeps source facts separate from voice and presentation.

Inputs to the writer

  • Question and selected source context.
  • Source IDs such as [S1].
  • Requested shape, length and tone.
  • Optional persona/style examples as voice guidance only.
  • Ownership and numerical-accuracy constraints.

Checks after writing

  • Malformed or unknown source IDs.
  • Claims supported by the cited passages.
  • Correct employer and personal ownership.
  • Answer completeness and relevance.
  • No invented outcomes, people or metrics.

One rejected draft can be revised using its original text, specific review feedback and the same evidence. Feedback is not treated as new factual evidence. The revised draft is checked again. Invalid supportive passage IDs fail closed after the bounded schema retry; invalid IDs in an insufficient decision are discarded without turning the decision into support.

The UI's verified field has two meanings: source extraction completed for the dedicated stack path, or application/model checks accepted a generated answer. Neither independently proves the underlying employment fact. The collaboration fallback uses additional rule-based cues; those cues reduce one observed failure and are not a complete semantic understanding of teamwork.

Why a correct answer could be rejected: the writer and checker can disagree about a paraphrase, a number qualifier, citation grouping or the exact question. Our fixes improved diagnostics, citation parsing and source-only repair. We did not disable support checks to force more answers through.

Natural voice: prompts now discourage forced informality, repeated filler, library labels as project names and numerical exaggeration. Your current local launcher uses general style instructions rather than a rich collection of personal writing samples. Temperature 0 still permits variation.

CHAPTER 06

The code map

Select a module to see its responsibilities and the kinds of changes that belong there.

app.py

The question screen

Renders the form, model/length/tone controls, actual index mode and evidence panel. Calls pipeline.draft() for V2.

Change here when…

Change a control, add a “show citations” preference, or display clear failure details. Keep factual logic in the backend.

question.py

Question type and answer shape

intent(), guidance(), search_question(), names_only_stack(). Rules recognize stack lists, introductions, experience stories and direct questions.

Change here when…

Add a comparison intent: recognize comparison wording, retrieve evidence for both subjects, instruct a compact comparison, then test mixed questions.

retrieval_v2.py

The evidence engine

prepare_chunks(), build_index(), bm25(), fuse(), eligible(), retrieve_candidates(), ground(). Handles source status, indexing, search, evidence selection and context.

Change here when…

Change chunk boundaries or candidate count; preserve employer/version metadata and re-evaluate wrong-source and missing-evidence cases.

answer.py

Draft writing and stack extraction

extract_stack() renders a list from a dedicated reviewed stack source. build_prompt()/generate_answer() handle prose, tone, length and optional structured stack fallback.

Change here when…

Change the answer contract or add a tone. Formatting changes must not add facts. Keep persona/style examples separate from evidence.

pipeline.py

The V2 coordinator

draft() handles focused clarifications, grounding, extraction, citation validation, model review, one revision and the final result.

Change here when…

Change a retry policy or add a completeness check. Never accept an unsupported draft merely to increase answer rate.

llm.py

Model clients

chat() creates/caches clients by model and temperature. Bolt E4B disables its thinking mode in the request. The cache holds clients, not answer history.

Change here when…

Choose a model that passes generation and structured-output tests. Registry entries are not proof that provider endpoints remain available.

config.py

Configuration and paths

Settings/get_settings() read environment values. V2 index paths resolve against the project. V1 and V2 indexes stay separate.

Change here when…

Add a setting with a sensible default and validation; do not place credentials in source or the guide.

cli.py

Commands

Supports ingest, answer and evaluate. Use --version v2 explicitly: the CLI default still selects V1.

Change here when…

Expose a backend setting as a command flag, then test both CLI and UI callers.

evaluation.py + tests/

Evidence about behavior

The fixture runner compares retrieval and coverage. pytest checks routing, metadata, citations, retries and persistence. Personal live audits stay local.

Change here when…

Add reviewed questions with expected sources, supported claims, answer shape and expected abstention. Keep independent questions for final evaluation.

../corrective-rag/src/crag/ingest.py

Shared document loading

load_documents() reads MD/TXT/PDF; chunk_documents() uses RecursiveCharacterTextSplitter. V2 reuses these functions.

Change here when…

Add format adapters here or in a new ingestion module, then update prepare_chunks() to preserve their metadata.

V1 versus V2: V1 reuses CRAG similarity search and optional per-chunk grading. Fast mode treats nonempty retrieval as coverage; grader errors retain chunks. V2 separates source eligibility, question shape, sufficiency and answer checks. Each version has a separate index.

LangGraph distinction: the original CRAG package has a LangGraph state machine with query rewriting and web fallback. Experience Copilot V2 coordinates Python functions instead. Installed dependencies do not mean every framework or feature is active on the V2 path.

CHAPTER 09

Implement a new answer requirement

Turn a vague preference into a question type, an evidence requirement, an answer contract and an evaluation case.

Make all interview answers shorter

Change points: answer.py: LENGTH_SPEC; app.py/cli.py defaults

  1. Define the desired spoken duration and word range.
  2. Change the relevant length instruction, not the evidence filter.
  3. Retain the central action, result and required citations.
  4. Test a short factual answer, broad introduction and multi-part story.
For a short answer: 3–4 clear sentences, about 80 words. Lead with the answer; include one supported example. Omit a metric when none is documented.
Add leadership / STAR answers

Change points: question.py; answer.py; source documents; tests/

  1. Write a real episode: situation, responsibility, collaborators, actions, reporting and outcome.
  2. Mark its source status and exact personal ownership.
  3. Route leadership questions to that episode and specify the desired structure.
  4. Check that coordination is not rewritten as managing direct reports.
Situation → my responsibility → actions → supported outcome. Do not invent team size, conflict, direct reports, praise or measurable impact.
Add comparison questions

Change points: question.py; retrieve_candidates(); answer.py

  1. Recognize the comparison without forcing it into a technology-only list.
  2. Retrieve and preserve sources for both subjects.
  3. Render dimensions such as purpose, contribution, technologies and result.
  4. Test missing evidence for one side; do not fill the gap from the other employer.
Compare the two documented projects on the requested dimensions. Keep separate source IDs and attribution. Say when one dimension is not documented.
Make answers sound more like me

Change points: profile/style_examples.md; EXP_STYLE; TONE_SPEC

  1. Collect a few genuine writing or spoken-answer samples.
  2. Use them as style examples, not employment evidence.
  3. Ensure the active launcher points EXP_STYLE at that file.
  4. Evaluate naturalness separately from factual support.
Use my direct sentence structure and vocabulary. Preserve source facts exactly. Do not copy factual achievements from style examples.
Add screenshots and scanned PDFs

Change points: load_documents(); format adapter; prepare_chunks(); evidence UI

  1. Detect whether the file has a usable text layer.
  2. Run OCR/layout extraction when necessary; keep the original.
  3. Retain page/region/quality metadata through prepare_chunks().
  4. Review extraction, especially numbers and tables, before inclusion.
  5. Test both retrieved content and citations to original page regions.
Adapter output: text + source + page + region + extraction method + quality indicators. The parser output is not automatically confirmed evidence.
Restore vector + keyword retrieval

Change points: EXP_V2_EMBED_MODEL; build_index(); retrieve_candidates()

  1. Probe the configured embedding model with passage and query inputs.
  2. Build a new hybrid snapshot in a separate index path.
  3. Use the same embedding model for stored passages and questions.
  4. Compare keyword versus hybrid with fixed source/answer labels.
  5. Check status, employer filters and latency before changing the active index.
python -m copilot.cli ingest --version v2
# Requires a working embedding endpoint; do not mix models inside an old vector collection.
A complete requirement example

“For a stack question, return technology categories with source citations and no responsibilities paragraph.” That is observable and testable. “Make it smarter” is not.

# A real, reviewed episode
Situation:

What I communicated:

This is a knowledge-base document. It is not automatically a model-training example. If the story is incomplete, a writing prompt cannot legitimately invent the missing people, conflict or outcome.

CHAPTER 10

Add PDFs, images and other formats

The ingestion adapter changes first. The later search and answer stages can often be reused.

InputNeeded ingestion workCurrent support
Markdown / TXTRead text; preserve headings and evidence labels.Implemented; Markdown is not deeply parsed into an AST.
Text-based PDFExtract existing text and ideally retain page/layout references.Basic pypdf extraction; pages currently joined.
Scanned PDF / screenshotOCR or vision-based parsing, reading-order/layout checks and page regions.Not implemented.
WordExtract headings, paragraphs and tables; handle comments/revisions deliberately.Not implemented.
Spreadsheet / CSVRetain sheet, headers, row keys, units and cell or table location.No structured spreadsheet adapter in this app.
Diagram / chartInterpret arrows, legends and relationships; OCR alone may miss meaning.Not implemented.
Audio / videoTranscription with speaker/time provenance; review uncertainty.Not implemented.

The adapter contract

{
  "text": "Extracted passage",
  "source": "original-document.pdf",
  "page": 4,
  "section": "Project results",
  "region": "table-2",
  "extraction_method": "ocr-with-layout",
  "source_version": "content-hash",
  "quality_status": "needs-review"
}

Adding OCR alone is not enough. Our current PDF loader joins page text and prepare_chunks() reconstructs metadata. Both stages must be updated to preserve page/region metadata, followed by citation rendering in the UI. Metadata types must also be compatible with the selected index store.

Review numerical extraction carefully: 10+ misread as 100 becomes a false fact even if retrieval works perfectly. Preserve table headers and units. A diagram's arrows may require a vision/layout interpretation step; keep direct extraction separate from model inference.

Optional future tools include a document conversion framework such as Docling. It is not installed or integrated as part of this guide. The configured embedding model's multimodal capability also does not make our text-only ingestion calls automatically accept raw images.

Primary documentation: pypdf text extraction and OCR limits · Docling supported formats · NVIDIA embedding overview

CHAPTER 11

Indexing, prompting and training are different

We have changed the application around an existing model. We have not changed model weights.

MethodWhat changesWhat it can help with
IndexingSearchable source records or vectors.Finding up-to-date evidence. It does not teach writing style.
Prompt engineeringInstructions sent with each request.Shape, tone, factual boundaries and evidence-review criteria.
Few-shot examplesExample questions and ideal answers included in a prompt.Demonstrating a desired format or voice; factual examples must not leak into unrelated answers.
Fine-tuningModel weights through a training process.Potentially more consistent style or task behavior, given a suitable model/service and curated data.
EvaluationQuestions, source labels and review criteria used to measure behavior.Finding regressions. Testing does not update model weights by itself.

Fine-tuning is not the first repair for missing stories, wrong employer labels, bad OCR or a search query that never finds the right passage. If training later becomes worthwhile, curate representative questions and high-quality answers, remove unsupported claims, and keep independent evaluation data. Continue to retrieve changing employment facts rather than relying on memorized facts.

Style examples guide presentation; they are not factual evidence. The current persona/style files are not a learned personal model. Training infrastructure, dataset upload, optimization runs, fine-tuned checkpoints and deployment of a trained custom model have not been implemented.

CHAPTER 12

Test improvements and diagnose failures

Measure the failing stage, not only whether the website returned text.

SymptomInvestigateUseful test
Correct passage never retrievedLoader, chunking, query expansion, aliases, search mode.Expected source recall and ranking on labeled questions.
Correct passage rejectedEvidence sufficiency and schema handling.Supported question with a direct source quote; inspect rejection reason.
Wrong answer formatRouting, answer contract, rendering.Stack-only versus story-plus-tools; paraphrased and mixed intents.
Cited but unsupported claimSource quality, attribution and claim review.Wrong-employer, unsupported metric, overstated ownership, malformed citation.
Supported but evasive draftQuestion completeness and retry feedback.Ask for a result or a leadership role and check it is actually addressed.
Awkward wordingStyle instructions, examples and model capability.Review naturalness independently from factual support.
Unexpected abstentionMissing story versus system/model error.Label expected abstentions and count service/schema failures separately.

A meaningful evaluation row

question: What did I own on this project?
expected_sources: [reviewed project note]
required_claims: [specific contribution]
forbidden_claims: [owned entire platform, managed direct reports]
expected_shape: concise first-person explanation
expected_abstention: false
review: factuality / completeness / citations / naturalness

The last completed offline suite in this work passed 72 tests. Tests cover particular behaviors; they do not prove every future answer correct. Live audits used fictional fixtures first, then selected personal documents after approval. Some old holdout questions had already been inspected; those results are not a pristine independent benchmark.

Commands

python -m pytest

python -m copilot.cli answer "Tell me about yourself" --version v2

Use the environment's Python interpreter, such as ..\.venv\Scripts\python.exe, when dependencies live in a virtual environment. The CLI currently checks for an API key even before a keyword-only ingest, despite that ingest not needing embedding calls. Fix that validation boundary if offline indexing becomes a product requirement.

Before calling a change an improvement: define the requirement, add supported/unsupported/ambiguous examples, test the stage in isolation, run the full answer path, review claims and voice, then evaluate untouched questions. Keep source files and keys out of public commits.
CHAPTER 13

What to improve next

Build from measured weaknesses rather than adding frameworks by default.

PriorityConcrete next changeSuccess condition
1 · Source completenessAdd real leadership, collaboration, reporting and conflict episodes with bounded ownership.The app can answer relevant behavioral questions without inventing people or outcomes.
2 · ConfigurationReplace scattered constants with validated settings and a documented answer-policy configuration.A new requirement can be changed in one clear place with regression tests.
3 · Retrieval evaluationCompare keyword and restored hybrid search on new personal questions with expected passages.Higher relevant-source coverage without wrong-employer or unsupported-answer increases.
4 · Alias handlingStore reviewed employer/project aliases instead of relying only on literal label matching.“IU”, “HuBMAP” and other approved aliases scope to the correct evidence.
5 · Document adaptersAdd OCR/layout or Word/spreadsheet adapters with provenance preservation.Correct extraction and original-page/table citations, not just more files ingested.
6 · ObservabilityRecord stage timing, route, source IDs, schema/service errors and review outcomes locally.An unexplained rejection can be diagnosed without guessing or exposing secrets.
7 · Conversation stateTrack a selected story and resolve “that project” in follow-ups.Multi-turn questions preserve employer/story scope. This is not currently a complete conversational-memory system.
8 · Optional trainingConsider fine-tuning only after enough reviewed examples and a stable evaluation set exist.A measured style/task improvement that cannot be obtained more simply through sources, rules or prompts.
